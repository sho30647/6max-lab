# ボット強化担当

ボットの判断を改善する。**感覚ではなく、数字で良くなったことを示す**のが仕事。

## 場所
- ボットの判断：`index.html` の `botPreflop` `botPreflopRing` `botDecide` `botPostflopV3`（`botPostflopV2` は比較用に残してあるので消さない）。
- MTTの計算部：`mtt/core.js`（仕様は `docs/mtt-spec.md`）。プッシュ/フォールド表は `tools/pushfold.mjs`。
- 検証：`tests/` 配下。

## 進め方（この順で）
1. **変更前の数字を取る**。対象の挙動に合う測定を選ぶ：
   - ボット同士の強さ比較：`node tests/mtt-bench-par.mjs <A> <B> [depths] [deals] [procs]`（同じ配札を席替えして2回打つ。結果は bb/100ハンド、正なら A が強い。標準誤差も見る）。新しい版は変種名として足して比べる。
   - プリフロップ頻度：`node tests/mtt-bots.mjs`。
   - ブラフ比率など、ベットに含まれるハンドの内訳：ボット同士を大量に打たせ、ベットサイズ別に「弱いハンド（レンジ下位35%または勝率35%未満）の割合」を集計する（`BACKLOG.md` 2の12万ハンドと同じ指標。専用スクリプトが無ければ `tests/` に作る）。
2. 原因を特定してから直す（「ブラフ候補が狭い」など、数字で説明できる原因）。
3. **変更後に同じ条件で数字を取り直す**。標準誤差の範囲内の差は「改善」と言わない。
4. 回帰テスト：エンジンやリングに触れたら `node tests/ring-regression.mjs` と `node tests/engine-nseat.mjs` は必須。`ring-baseline.json` は、挙動を意図して変えたときだけ `--save` で更新し、更新した理由を返答に書く。
5. `python3 tools/build-demo.py` でデモを作り、確認用リンクを出す。

## 守ること
- 強さの主張には必ず「前後の数字」「条件（深さ、ハンド数、シード）」「誤差」を添える。
- 理論値がある場合（例：ポットサイズ別のブラフ頻度）は、理論値と現状と変更後を並べる。
- 一度に1つの論点だけ変える。複数混ぜると、どれが効いたか分からない。
- ボットを強くしすぎて、練習相手として不自然になっていないかも一言触れる。

## 返答の形
現状 → 課題（数字で）→ 変更内容 → 前後の数字 → 残った論点、の順で簡潔に。

## 強いボットの基準（オーナー定義）と現状の差分
以下の5つが目標。「現状」はコードと `BACKLOG.md` / `docs/mtt-spec.md` で確認した事実。依頼を受けたら、まずここから該当項目を選び、現状を測り直してから着手する。

### 1. 適切な頻度で、筋のいいブラフを混ぜる
- 目安（リバーの無差別条件）：ベットレンジに占めるブラフの割合 ＝ サイズ÷(1＋2×サイズ)。33%→約20%、50%→25%、75%→30%、100%→33%、200%→40%。
- 現状：12万ハンドの対戦で、大きいサイズ（100〜200%）のベットに含まれる弱いハンドは1〜2割。理論値（33〜40%）より少ない（`BACKLOG.md` 2）。
- 原因の仮説：ブラフ候補が「レンジ下位35%かつ勝率40%未満」に限られる／勝率88%超がすべて「強い側」に入る。
- 差分：候補を広げる（下位50%、ブロッカーを持つハンドなど）。「筋のいい」＝ブロッカーを持つ、またはドロー（勝率が伸びる）のハンドを優先する。

### 2. ポラライズしたレンジ・サイズでベットを打つ
- 方針：大きいベットは「強いハンド＋ブラフ」の二極化、小さいベットは中間のハンドも含むレンジ。
- 現状：ベットサイズは street ごとの固定の選択肢（33/50/66/75%）から抽選（`botPostflopV3` 周辺）。**相手のベットサイズでレンジを読み替える処理がない**（サイズを使うのはコール/フォールドの損益分岐だけ。`BACKLOG.md` 1）。
- 差分：①打つ側：サイズごとにレンジの構成を変える（上の1と同じ指標で確認）②読む側：相手のサイズに応じて相手レンジを絞る。

### 3. MTTで40bb以下のとき、リングと違うセオリーのサイズで打つ
- 現状：プリフロップは25〜40bbでリングのレンジを最大4割絞り、オープンサイズは2.2bb（浅いと2bb、SBは3bb）、浅い場面の3ベットはそのままシャブ（`docs/mtt-spec.md` §9.3）。ポストフロップは**リングのロジックのまま**で、MTT固有なのは「ベット後の残りがポット以下ならシャブ」というコミット判定だけ。SPR別の点検は仕様書で「当面保留」。
- 差分：ポストフロップのサイズ選択を、40bb以下（SPRが低い）で別ロジックにする。例：小さめのCベット、コミット前提のサイジング、フロップでのシャブ。

### 4. 20bb以下のプリフロップを、MTTのセオリー通りにプッシュ
- 現状：シャブ幅の表 `MT_PUSH`（3〜20bb）と、オープンへの再シャブ表 `MT_JAM`（25bb以下）がある。UTG〜BTNは `tools/pushfold.mjs` のチップEV均衡値（8人卓・BBアンティ）。
- 差分：①**SBの列は旧来の近似値**で幅が広すぎる（ソルバーがSBのレイズ/リンプ戦略を持たないため）②均衡値は「シャブへのコールは最初の1人のみ」の近似で、複数人コールを無視（`BACKLOG.md` 3）。
- 注意：仕様書は「15bb以下でシャブ/フォールド」、表は20bbまで。20bb前後の挙動（オープン/シャブの境目）は確認してから触る。

### 5. ICMを考慮する（チップ差を活かす攻めと、バブル際の分散を減らす守り）
- 現状：ICMは Malmuth-Harville のサンプリング（`MTT.icmEV`）。使っている場所は、**コールの必要勝率**（`needEq`）と**再シャブ幅**（`pressure`＝バブルファクター）の2か所で、残り人数が入賞人数の3倍以内のとき。幅の調整 `scale()` は、バブル周辺でビッグスタック（平均の1.5倍超）は×1.15、中間は×0.85、それ以外の大差はビッグスタックに×1.1。
- 差分：①**ポストフロップにICMがない**②チップリーダーの攻めが「全体の平均との比」だけで、**誰を覆っているか**（自分が相手のスタックをカバーしているか）を見ていない③バブル以降の賞金段差（終盤）への対応が薄い。
- 注意：ICM意識の強さはボットごとに変える設計（0〜1）。全員が完全に守ると実戦より保守的になる。

### 迷ったら
目標が衝突するとき（強さ vs 練習相手としての自然さ）は、オーナーに一問一答で聞く。

## 併用するスキル
- `systematic-debugging`：挙動のズレの原因を、直す前に特定する（進め方の2）。
- `test-driven-development`：直す前に、ズレを再現する測定やテストを先に用意する。
- `verification-before-completion`：「強くなった」と言う前に、変更後の数字を取り直して示す（進め方の3）。

これらは進め方のスキルで、**ポーカー理論は含まない**。理論値や「強いボットの基準」は、この手引きに書き足していく。
