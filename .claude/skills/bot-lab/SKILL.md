# ボット研究所（夜間ループ）

毎晩 2時・3時・4時・5時（日本時間）に、新しいセッションとして起動される。**各回は前の回の記憶を持たない。** 記憶は次の3つのファイルだけ。

- `docs/bot-lab/policy.md`：方針書（オーナーが書く。読むだけで、書き換えない）
- `docs/bot-lab/league.json`：チャンピオン、エクスプロイト役の一覧、チャンピオンの偵察結果、交代の履歴
- `docs/bot-lab/journal.md`：実験ノート（毎ラウンド追記）

測定の生ログは `docs/bot-lab/results.jsonl` に自動で追記される。

## 0. 始める前に（毎回）
1. `TZ=Asia/Tokyo date` で時刻を確認する。**その時の :50 までに**ラウンドを終え、コミットとpushを済ませる。5時の回は :35 までにラウンドを終え、残りの時間で朝のレポートを書く。
2. 作業ブランチ：`claude/bot-lab-nightly`。origin にあれば checkout して pull、なければ `staging` から作る。ただし `staging` に `docs/bot-lab/` がまだ無いあいだは、`claude/bot-lab` から作る。前夜のPRがマージ済みなら、`staging` から作り直す（CLAUDE.md のマージ済みブランチの扱いに従う）。
3. `policy.md` を全部読む。`journal.md` は最後の3件、`league.json` は全部読む。
4. **オーナーのメモ**：`docs/bot-lab/owner-notes.md`（作業ブランチのもの）を読む。メモは、オーナーが会話で送ったものを、会話側が作業ブランチ `claude/bot-lab-nightly` に追記する。`journal.md` にまだIDが出てこないメモが「未処理」。扱い方はメモ用ファイルの冒頭に書いてある（仮説として扱い、測れる形にして測り、結果を `journal.md` と朝のレポートに書く）。

## 1. 1ラウンドの流れ
1. **偵察**：`league.probe` が今のチャンピオンのものでなければ、`node tests/ring-league.mjs probe <チャンピオン> 1000 1 --save`（約17分）。
1.3. 未処理のオーナーのメモがあれば、論点を選ぶ前に、測れる形にして測る（測るだけで、実装は論点の選択ルールに従う）。結果は `journal.md` に「N○：…」として書く。
1.4. 8章の精度向上の変更（物差し：方針書の8.3）は、採用の基準も8.4を使う（強さの改善は必須にしない）。
1.5. **方針書の8章（オーナーの理論）が、チャンピオンにまだ実装されていなければ、偵察より先に、8章の「進め方の目安」の次の1段階を今日の論点にする**（挑戦者は、新しい版番号として `BOT_TWEAKS` に足す。理論の適合度の確認が、判定に加わる）。8章の実装が一通り終わったら、2以降の「穴の選択」に戻る。
2. **穴の選択**：偵察で「* leak」（勝ち額が95%の誤差を超える）の役のうち、勝ち額が一番大きいものを今日の論点にする。オーナーへの確認はいらない。**平均が大きくても誤差の範囲内の役は、穴として扱わない。**
   - 同じ論点で2晩続けて不採用なら、その論点は「保留」として実験ノートに理由を書き、次に大きい穴か、新しい役の発見に移る。
   - 穴が1つもなければ、**新しいエクスプロイト役を考えて** `league.json` に足し、その役だけ測る（`node tests/ring-bench-par.mjs <チャンピオン+delta> <チャンピオン> 1000 4 1`）。必要なら新しいつまみを `botPostflopV3` に足す（つまみを指定しない版の挙動は変えないこと）。方針書の5（オーナーの観察）で、まだ役になっていない弱点から優先する。
3. **仮説**：その役が勝つ理由を、コードの該当箇所で説明する（例：「ドローの勝率を2枚分で見ているので、大きいフロップベットに払いすぎる」）。説明できなければ、`node tests/ring-bench.mjs stats <チャンピオン>` で該当場面の数字を取る。
4. **挑戦者を作る**（1つの論点につき1〜2体）：
   - (a) 勝った役のずれ自体を取り込む（例：`drawTight` が勝った → `<チャンピオン>+drawEq=0.6+impl=0`）。
   - (b) 穴を塞ぐコードの修正（新しいつまみで表現し、既定値では挙動を変えない）。
5. **判定**：`node tests/ring-league.mjs eval <挑戦者> --target=<論点の役> 1000 1`（約18分）。PASS なら `node tests/ring-league.mjs confirm <挑戦者> --target=<論点の役> 1000 101`（別シードで、直接対決・論点の役・上位3役だけ測り直す。約12分）。方針書の4の基準をすべて確認する。
   - 誤差が±4を超える役（ずれの大きい役ほど誤差が大きい）は、平均だけ見て穴と判断しない。必要なら、その役だけ別シードで足して測る（`node tests/ring-bench-par.mjs <A> <B> 1000 4 <シード>` を2〜3回）。
6. **交代**（両方 PASS のときだけ）：
   - `BOT_TWEAKS` に新しい番号（いまの最大＋1）で挑戦者のつまみを足し、`RING_VER` をその番号にする。コメントに、何を直したかを1行足す。
   - 画面の版の表示も揃える：`#fBot` の `<option>` と、`COL_DOC.bv` の説明に新しい版を足す。
   - `node tests/ring-regression.mjs --save`（理由を実験ノートに書く）と、`tests/ring-*.mjs`、`node tests/engine-nseat.mjs` を通す。`tests/ring-bot-v6.mjs` のように版の番号を見ているテストは、新しい版に合わせて直す（テストの意図は変えない）。
   - `league.json`：`champion` を新しい番号に、`history` に `{date, from, to, why, worstBefore, worstAfter}` を足し、`node tests/ring-league.mjs probe <新チャンピオン> 1000 1 --save`。
7. **記録**：`journal.md` に1ラウンド分を追記する（下の形）。不採用でも書く。
8. **コミットしてpush**（1ラウンド1コミット）。PRが無ければ `staging` 向けに作る（タイトル「夜間ボット研究」、本文は実験ノートの要約）。あれば本文を更新する。`main` には触らない。

時間が余れば、次のラウンドに進む。**ラウンドの途中で時間切れになりそうなら、測定を始めない。** 測定の途中で止めた結果は使わない。

## 2. 実験ノートの形
```
## 2026-10-20 02:05 ラウンド1
- チャンピオン：6（穴：riverBluff4 +3.1 ± 1.6）
- 論点：drawTight（フロップのドローのコールが損）
- 仮説：...（コードの箇所）
- 挑戦者：6+drawEq=0.6+impl=0
- 結果：直接対決 +1.1 ± 1.4、論点の役 3.1 → 0.4（シード1）、0.6（シード101）、新しい穴なし → 採用 / 不採用（理由）
- 自然さ：ベットを受けたときのフォールド率 F M 48%（理論の最低防御 67%→フォールド33%以下）…
- 次の候補：...
```

## 3. 朝のレポート（5時の回の最後）
`docs/bot-lab/reports/YYYY-MM-DD.md` に書いてコミットする。オーナーが朝に読むもの。
1. 結論（1〜2行）：チャンピオンは替わったか、穴（誤差を超えて勝つ役）はいくつ・どれだけ減ったか。
2. オーナーのメモへの回答（N○ごとに：測った方法、結果、論点にしたか）。
3. 昨夜のラウンド（論点、仮説、前後の数字、採用・不採用と理由）。
4. 練習相手としての変化（オーナーが打って気づきそうな変化を、具体的な場面で1〜3個）。
5. 次の夜の候補。
6. オーナーへの質問（方針書で判断できなかったこと。一問一答で1つまで）。

そのあと `python3 tools/build-demo.py` でデモを作り、CLAUDE.md のデモのURLを更新して、レポートの末尾にリンクを書く。使えるなら、プッシュ通知でレポートの要約を送る。

## 3.5 マージ滞留のアラート（5時台の回、毎日）
`git fetch origin staging` のあと、`git log origin/staging..HEAD --format=%ct | tail -1` で、`staging` に入っていない一番古いコミットの時刻を取る。**それが3日（72時間）以上前なら、アラートを出す。** `staging` に入っていない夜間のコミットが無ければ、何もしない。
- 朝のレポートの**一番上**に、「⚠ 夜間の変更が○日間 `staging` にマージされていません（未マージのコミット○件）。PRの確認とマージをお願いします」と書く。PRのURLが分かれば添える。
- プッシュ通知の道具（`PushNotification`、ToolSearch で `select:PushNotification` と引いて読み込む）が使えれば、同じ内容を1行で送る。使えなければ、レポートの冒頭だけでよい。
- マージされるまで、毎朝繰り返す。

## 4. してはいけないこと
- 方針書を書き換える。採用の基準を夜の途中で緩める。
- `main` へのpush、`main` 向けのPR、PRのマージ。
- MTT、プリフロップ、画面のデザイン、`firestore.rules` に触れる（版の表示の追加は除く）。
- 測定していない改善を「強くなった」と書く。誤差の範囲内の差を改善と書く。
