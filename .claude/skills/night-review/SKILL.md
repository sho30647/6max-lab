# 夜間の判断審査（新ボット）

毎晩、予約で新しいセッションとして起動される。**前の回の記憶は無い。** 記憶は `docs/hand_reviews.md`（審査の記録）と `docs/night-review/`（毎晩のレポート）だけ。

**この作業はボットを直さない。** 直すかどうかはオーナーが朝のレポートを見て決める（オーナーの方針、2026-10-26）。

## やらないこと（必ず守る）
- `bot/`・`index.html`・`mtt/`・`docs/postflop_spec.md`（指示書）・`docs/decisions.md` の変更。ボットの数字（`params.js`）の変更。
- `main` や `staging` へのマージ、`main` 向けのPR。
- 指示書の考え方を変える案の採否を決めること（オーナーが決める。CLAUDE.md）。

## 0. 始める前に
1. `TZ=Asia/Tokyo date` で日付を確認する（レポートの名前に使う）。全体で2時間以内に終える。
2. 作業ブランチは `claude/night-review-log`。
   - origin にあれば checkout し、`git merge origin/staging` で最新のボットを取り込む（衝突したら、記録のファイルは両方の行を残す）。
   - 無い、またはそのPRがマージ済みなら、`origin/staging` から作り直す（`git checkout -B claude/night-review-log origin/staging`）。
3. `docs/hand_reviews.md` を全部読む（既に審査した原因を知るため）。

## 1. 探す（機械、約60分）
```
mkdir -p docs/night-review
node tests/spec-scan.mjs --minutes=60 --out=docs/night-review/latest-scan.json
```
- 新ボット同士で打ち、ボットの判断を1つずつ「別の手（降りる↔コール、チェック↔ポットの2/3のベット）」でやり直して、結果の差を測る。似た局面をまとめた「グループ」ごとに、差の平均が、ばらつきを考えても0より大きい（99%）ものを、損の大きい順に最大3つ出す。各グループに、平均に近い見本のハンドが2つ付く（相手の手札は入れていない）。
- 結果が `FAIL` を出したり、途中で止まったりしたら、審査はせず、何が起きたかをレポートに書いて 4 へ進む。
- 上位が0件なら「今夜は目立つ損は見つからなかった」と書いて 4 へ進む。

**読み方の注意**：相手はボット自身なので、「別の手が得だった」のは、ボットの穴のせいとは限らない。相手側（同じボット）の応じ方の穴（例：ベットに降りすぎる）のせいのこともある。どちらなのかは、bot-judge が理論で決める。

## 2. 審査（bot-judge）
上位のグループごとに、次のように進める。
1. **既出か確かめる**：`docs/hand_reviews.md` に、同じ局面（ストリート・場面・アクション）で同じ根本原因の行があり、「オーナーの判断待ち」か「対応中」なら、審査し直さない。レポートに「既出（#番号）。今夜も出た：件数・損の大きさ」とだけ書く（何度も出ること自体が、優先度の材料になる）。
2. 新しいものは、`bot-judge` エージェントに渡す（グループ同士は独立なので、並行で呼んでよい）。依頼文には、次を全部書く（bot-judge は会話を見ていない）。
   - 見本のハンド1つ目のハンドヒストリー：ライン、ポジション、有効スタック、プリフロップ、それまでのアクション（bb）、スート付きのボード、ボットの手札、ボットのアクション。`latest-scan.json` の `top[i].hands[0]` の項目をそのまま、読みやすく並べる。
   - 判断トレースの全文（同じ項目の `trace`）。
   - 相手の情報：「相手は同じ新ボット（`bot/spec/`）。実際のレンジは `bot/spec/` から分かる」。
   - 機械が見つけた理由：グループ名、件数、別の手との差の平均（bb）、100フロップあたりの損、注意（相手が自分なので、相手側の穴の可能性もある）。2つ目の見本のハンドも、参考として付ける。
   - 頼むこと：「`bot-judge.md` の返答の形（7項目）で。ボットが理論上正しいなら、そう言い切り、別の手が得になった理由が相手側（同じボット）の応じ方の穴かを見て、そうならその穴を、原因と直し方の形で書いて。指示書の考え方の変更に当たる案は、採否を決めずに『オーナーの判断事項』として、メリット・デメリットとおすすめを書いて。」
3. bot-judge が STEP0 で質問を返したら（情報が足りない）、見本の2つ目で頼み直す。それでも止まったら、その質問をレポートに書く。

## 3. 記録
- `docs/night-review/<日付>.md` に、その夜のレポートを書く：測った量（ハンド数・判断数・時間）、上位グループの表、各審査の7項目（bot-judge の返答をそのまま）、既出のもの。
- `docs/hand_reviews.md` の表に、新しく審査したものを1行ずつ足す（新しいものを上に）。局面の頭に「夜間」、対応は「オーナーの判断待ち（夜間 <日付>）」。ボットが正しいと判定したものも、「適切」として残す（同じ局面を毎晩審査し直さないため）。下に詳細の節（`## #番号 …`）を足す。番号は既存の続き。

## 4. 保存
1. `git add docs/night-review docs/hand_reviews.md` → コミット（メッセージ：`夜間審査 <日付>：<見つかった件数>件`）→ `git push -u origin claude/night-review-log`。
2. `claude/night-review-log` から `staging` 向けの、開いたPRが無ければ作る（題：「夜間の判断審査の記録」。変更は記録だけで、画面のファイルを含まない）。あれば、pushで足されるので何もしない。マージはしない。
   - 予約で動くセッションには GitHub のPR作成の道具が無いことがある。無ければPRは作らず、レポートに「記録はブランチ `claude/night-review-log` にある」と書く（オーナーが昼の会話で「夜間の記録を staging へ」と言えば、そのときにPRを作る）。

## 5. 朝のレポート（このセッションの最後の返答）
オーナーが朝にスマホで読む。CLAUDE.md の「オーナーへの返答・質問の書き方」に従う。
- 1行目：結論（例：「今夜は損をしている局面が2つ見つかり、1つは直す価値が高い」）。
- 見つかったものごとに3行まで：どんな局面か（ふつうの言葉で）、bot-judge の判定（ボットが不適切／適切、損の大きさ）、直すとしたら何を変えるか（指示書の範囲内か、考え方の変更か）。
- 詳しくは `docs/night-review/<日付>.md` とPRにあると書く。
- 最後に質問を1つだけ：冒頭に「答えてほしいのは：」。例：「直すものを番号で選んで（なし、も可）」。考え方の変更に当たるものがあれば、その採否を、メリット・デメリットを並べて選択肢で聞く（そのときは、この1問だけにする）。
