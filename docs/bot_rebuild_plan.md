# ポストフロップBot 作り直しの設計案（フェーズ1）

この設計案は、`docs/postflop_spec.md`（以下「指示書」）を実装するためのものです。対象は指示書のフェーズ1（Step0〜7）だけで、付録A（フェーズ2）は実装しません。付録Aは、あとから差し込めるように口だけ用意します。

8章のとおり、オーナーと方針が決まりました。段階1（エクイティエンジン）から実装を始めています。測って決めたことは `docs/decisions.md` に残します。

---

## 1. 現状の把握

### 1.1 ゲームの作り

- ゲーム全体は `index.html` の1ファイルです（約5,300行の JavaScript で、ビルドの工程はありません）。MTT の土台だけが `mtt/core.js` に分かれていて、`<script src>` で読み込んでいます。デモの生成（`tools/build-demo.py`）は、この2ファイルを1枚の HTML にまとめます。
- 実行場所はブラウザです。スマホでも動きます。サーバー側の計算はありません。
- 1ハンドの流れは次のとおりです。`playHandBody` → 各ストリートの `bettingRound` → 手番が来たら `botDecide(seat)` → 返った行動を `applyAction(seat, dec)` で反映します。
- ボット用の補助計算には、既存のものがあります。`equity`（モンテカルロ法。1回あたり170〜250回試行）、`narrowRange`（アクションごとにレンジを絞る）、`rangeTable` と `percentileOf`（レンジ内の順位）、`texture`（ボードの分類）です。

### 1.2 今のボット（ベースライン）

- ポストフロップは `botPostflop(seat)` が `p.ver` を見て振り分けます。`ver===2` なら `botPostflopV2`、それ以外は `botPostflopV3` です。V3 の上に `BOT_TWEAKS[RING_VER]` の調整が乗ります（現在は `RING_VER=13`）。
- 判断の順番は `docs/bot-logic-current.md` にまとめてあります。場面で全体の頻度 F を先に決め、手の順位で上から当てはめる作りです。
- `botPostflopV3` は MTT でも使われています（`MT.on` のときの分岐。ショートスタックや ICM の扱いを含みます）。
- 比較用のベンチマークがあります。`tests/ring-bench.mjs` は、Playwright で `index.html` を動かし、`p.ver` を変えて重複配牌で対戦させます。そのほか、リーグ戦（`ring-league.mjs`）、リバーの均衡とのズレ（`ring-river-gap.mjs`）などがあります。

### 1.3 ゲームとボットの受け渡し

**ボットに入るもの：** 引数は席番号 `seat` だけです。ボットは、グローバルの状態 `S` を直接読みます。

| 必要な情報 | 読み取り元 |
|---|---|
| 自分のハンド、スタック、今のストリートで出した額 | `S.players[seat].hole`、`.stack`、`.bet` |
| ボード、ストリート | `S.board`（カード番号は 0〜51。`rank=c>>2`、`suit=c&3`）、`S.street`（0=プリフロップ〜3=リバー） |
| ポット | `potTotal()` |
| 今の最大ベット、最小レイズ幅 | `S.currentBet`、`S.minRaise` |
| ベットとレイズの回数 | `S.raiseCount`（プリフロップは BB を1回と数えます。ストリートが変わると 0 に戻ります） |
| プリフロップのレイズ回数 | `S.pfRaises`（フロップの開始時に記録。1=リンプ、2=SRP、3=3BP、4以上=4BP+） |
| プリフロップのアグレッサー | `S.pfAggr` |
| 前のストリートのアグレッサー | `S.prevStreetAggr` |
| 今のストリートで最後に打った人 | `S.lastAggr` |
| ポジション | `isIP(seat)`、`postOrder(seat)`、`posOf(seat)`（BTN/SB/BB/UTG/HJ/CO） |
| 生き残っている人 | `S.players[i].folded`、`.allIn` |
| 行動の履歴 | `S.log[street]`（文字列。例：`"BTN b250"`）と各プレイヤーの `.la`（最後の行動） |
| ブラインド | BB は 100 チップ（`BB` 変数）。リングの初期スタックは 10,000 チップ（100bb） |

**ボットが返すもの：** `{act:'fold'|'check'|'call'|'raise', to:<このストリートでの合計額>}` です。ベットも `act:'raise'` で表します（`S.currentBet===0` なら、ベットとして記録されます）。

**ゲーム側の補正（`sanitize`）：** ボットの出した行動は、ここで次のように直されます。

- 払う額がある場面のチェックはフォールドに、払う額がない場面のフォールドやコールはチェックになります。
- レイズは `to ≥ S.currentBet + S.minRaise` に引き上げられます。額は `roundBet` で丸められます。
- ボットは、スタックの 90% 以上を出すならオールインになります。上限はスタックです。

つまり、新ボットは「金額を返す」だけでよく、最小額や丸めはゲーム側が保証します。ただし、ボットが見積もった額と実際に出る額がずれることはあるので、ログには丸めたあとの額を残します。

**レンジの更新：** `applyAction` の最後で、ゲームは全プレイヤーの `p.rw / rw2 / rw3` を絞ります（`narrowRange`）。これは旧ボットの仕組みです。ヒーロー向けの表示にも使われているので、触りません。

### 1.4 プリフロップレンジの形式

レンジの出どころは2つあります。

1. **共有チャート（`PFRanges`）**
   - 中身は `DEFAULT_RANGES` を土台に、管理者が Firestore で編集した表（`SharedRanges`）を重ねたものです。
   - 対象はリングの `open`（オープン）、`vsOpen`（オープンへの対応）、`vs3bet`（3ベットへの対応）です。キーは `"BTN"`、`"BBvsBTN"`、`"BTNvsBB"` のような形です。
   - 形式：`{size, h:{"AKs":{r,c,j}, …}}`。169のハンドクラスごとに、レイズ・コール・オールインの頻度（0〜1）が入っています。残りがフォールドです。
   - **管理者がいつでも書き換えられます**（ゲームを開くたびに読み込みます）。
2. **組み込みチャート（`CH.*`）**
   - 共有チャートが無い場面だけで使います。リンプ後のアイソレート、間にコールがいる場面、コールド3ベット、スクイーズ、4ベット以上、オールインへの対応です。
   - 形式は `parseRange` の文字列から作った `Map(クラス→頻度)` です。

旧ボットは、プリフロップで行動するたびに `assignPreRange` で `p.rw`（Float32Array(1326)、`ALL` の順。重みは「そのアクションの頻度」）を作ります。ただし、**前のアクションの頻度は掛け合わせていません**。例えば BTN オープン → BB 3ベット → BTN コールの BTN のレンジは、`vs3bet` のコール頻度だけで、オープン頻度を掛けていません。また、重みは 169 クラス単位で、スートの組み合わせ（コンボ）は均等です。

指示書が求めるのは「ポジション×ライン別の、コンボ単位の重み付きレンジ」なので、**変換の層が要ります**（3.2）。

### 1.5 計算速度の実測

この環境の Node で、既存の `evalHand`（7枚の役判定）を測ると、毎秒約 740 万回でした。スマホのブラウザでは、これの数分の1と見込みます。

## 2. 基本方針

| 項目 | 方針 | 理由 |
|---|---|---|
| 旧ボット | `index.html` の `botPostflopV2/V3` と `BOT_TWEAKS` を**一切変えずに残す**。名前は「v13（ベースライン）」と呼ぶ | 比較の基準 |
| 新ボットの置き場所 | 新しいディレクトリ `bot/spec/`。複数の JS ファイルにする。`mtt/core.js` と同じく、ブラウザでも Node でも読める形にする | 1ファイルの `index.html` をこれ以上太らせない。単体テストを Node で回せる |
| 差し替えの口 | `botPostflop(seat)` に1行足すだけにする。`p.ver==='spec'` のとき `SpecBot.decide(seat)` を呼ぶ。新ボットが例外を出したら、旧ボットの判断で続ける（ゲームを止めない） | 旧ボットと同じ入出力。ベンチマークは `ver` の指定だけで新旧を対戦できる |
| 対象 | リングゲームの SRP（3人以上を含む）、3BP、4BP+。リンプポットと、コールドコーラーがいる3BPは旧ボット。MTT（`MT.on`）は旧ボットのまま | 指示書は 100bb キャッシュが前提（8章の決定5） |
| 既定の切り替え | リングのボットを新ボットに替えるのは、評価が済んでオーナーが決めたあと。それまでの既定は旧ボット | 本番の挙動を変えない |
| エクイティ計算 | 対局中は JS の自前の厳密列挙（既存の `evalHand` を使用）。eval7 は検算と事前計算のクロスチェックに使う | 下の 2.1 |
| 数値 | すべて `bot/spec/params.js` の1か所に集める。指示書11章の区分（①②③）ごとに分ける | 後から調整しやすくする |

### 2.1 eval7 について（検討の結果）

eval7 は Python 用のライブラリです。このゲームはブラウザで動く JavaScript なので、**対局中には使えません**。Python をブラウザで動かす方法（Pyodide）もありますが、読み込みに数十MBかかるので不採用です。

使い道は次の2つにします。

1. **検算：** JS 側の役判定とエクイティ計算の結果を、eval7 と突き合わせます（`tools/equity_crosscheck.py`）。`pip` で入ることは確認済みです。
2. **事前計算：** Python と eval7 で作ることもできます。ただし、対局中と同じ JS のコードで作るほうが「事前計算と対局中で数字がずれる」心配がないので、**事前計算は Node（JS）で作り、eval7 で抜き取り検査する**ことにします。

### 3.2 プリフロップの変換層（`preflop.js`）

- 入力はプリフロップの行動の列です（誰が、どの場面で、何をしたか）。これは `applyAction` に入れずに、`S.log[0]` と各席の `raisedPre`、`called`、`S.firstRaiser`、`S.threeBettor` から組み立てます。
- 出力は、各プレイヤーのコンボ単位の重み `Float32Array(1326)` です。
- 重みは、**ラインに沿った各アクションの頻度の積**にします。例を示します。
  - BTN オープン → BB コール（SRP）
    - BTN：`open.BTN.r`
    - BB：`vsOpen.BBvsBTN.c`
  - BTN オープン → BB 3ベット → BTN コール（3BP）
    - BTN：`open.BTN.r × vs3bet.BTNvsBB.c`
    - BB：`vsOpen.BBvsBTN.r`
  - 4BP は、上に `vs3bet` の `r` / `j` と、組み込みの `CH.vs4` を掛けます。
- クラスからコンボへは均等に配ります（ペアは6通り、スーテッドは4通り、オフスートは12通り）。
- レンジの元データ（共有チャートの JSON）のハッシュを計算し、事前計算の表と一致するかを確かめます（4章）。

### 4.1 エクイティエンジン（`equity.js`）

- **ランアウト表：** 各ストリートの最初に、残りのカードの出方（フロップ 1,081 通り、ターン 46 通り、リバー 1 通り）ごとに、全コンボの役の強さを1回だけ計算して持っておきます。
- **レンジ対レンジの厳密計算：** 1つのランアウトの中では、役の強さで並べ、相手レンジの重みの累積から勝ち・引き分けを数えます。同じカードを使うコンボは、カードごとの累積を引いて除きます。これで、全コンボの「レンジに対するエクイティ」が、1ランアウトあたり並べ替え1回で出ます。
- **D と V：** フロップでは、上の集計を「どのターンが落ちたか」別に貯めると、ターン時点のエクイティが 47 枚分そろいます。そこから D（80%以上になる比率）と V（50%未満に落ちる比率）を計算します。追加の計算は要りません。ターンでも、リバーのカード別に同じことをします。
- **Ec など：** コールレンジやレイズレンジに対するエクイティは、同じランアウト表を使い、重みだけ替えて集計し直します。
- **見積もり：** フロップ全体で約 240 万回の役判定です。Node では約 0.3 秒、スマホでは 1〜1.5 秒と見込みます（段階1で実測）。
  - 目標の 0.5 秒を超えるときは、Web Worker（画面を止めない裏の計算）で、ボットの手番の前に計算を始めます。
  - それでも間に合わないときは、指示書0章のとおり、モンテカルロの回数を段階的に減らします。最後の手段は、テクスチャ表の初期値です。
- **モンテカルロ：** 試行回数は固定で、初期値は 5,000 回です。上の厳密計算が重すぎる場合の代わりとして残します。

### 4.2 事前計算（`tools/precompute-flops.mjs` → `bot/spec/data/`）

- **単位：** スートの入れ替えで同じになるフロップ（1,755 通り）×レンジの組です。
- **レンジの組：** SRP は 15 組です（オープンする側5ポジション×後ろのポジション）。3BP と 4BP も同じ 15 組ずつで、合計 45 組になります。どちらが IP かは、ポジションから決まります。
- **1行の中身：** RA、NA、実効RA（IP / OOP）、中間層の比率、テクスチャの5ラベル、静的・動的の値、ノードの型、目標頻度 F、サイズ候補、検算フラグ（テクスチャから想定される向きと逆なら立てる）。
- **大きさ：** 45 × 1,755 ≒ 7.9 万行で、JSON で約 3MB、圧縮すると約 1MB です。レンジの組ごとにファイルを分け（1ファイル約 70KB）、その組の初めてのハンドで読み込みます。
- **コンボ単位のバケット、D、V は、事前計算に入れません（指示書0章との違い）。** 理由は大きさです。45組×1,755フロップ×2人×1,326コンボで、約 2 億件（数百MB）になり、ブラウザに配れません。代わりに、4.1 の方法で、ハンド内に1回だけ計算します。指示書の「表を参照する」ことの狙い（対局中の重い計算を減らす）は、ハンドの最初に1回だけ計算することで満たします。
- **作り直し：** 元レンジのハッシュを表に書き込みます。
  - 対局中に共有チャートのハッシュと照合します。違えば、その組は対局中に計算してキャッシュし、空き時間に表全体を作り直します（8章の決定4）。
  - プリフロップレンジを変えたら、`node tools/precompute-flops.mjs` で作り直します。


- フェーズ1のコードは、`exploit` を読みません。読み出し口は、`hooks` の3つだけにします。

### 4.4 判断トレース（指示書12章）と振り返りログ（11章）

**考え方：** トレースは「判断に使った数値の控え」です。各ステップのモジュールは、計算した値をそのままトレースに書き込みます。説明文は、ハンドが終わってから、トレースの数値だけで作ります。判断の処理と説明の処理を分けるので、説明のために判断を変えることも、判断に無い理由を説明に足すこともできません。

**11章のログとの関係：** 別々に持たず、1つのレコードにまとめます。判断のときにトレース（状態・推定・判断）を書き、ハンドが終わったら同じレコードに「結果」と「照合」を足します。これが11章の振り返りログになります。

**入れ物（`trace.js`）**

```js
// 1アクションに1件。判断の入口（index.js）で作り、各モジュールに渡す
Trace = {
  v: 1,                       // 形式の版（テンプレートの読み替えに使う）
  hand: <ハンド番号>, seat, pos, hole:[a,b], board:[…], street, actionNo,
  step0: { potType, spr, sprClass, ip, initiative, nodeKind, nPlayers, pot, toCall, effStack },
  step1: { me:  { before:[b1..b5], after:[b1..b5] },     // バケット別の重みの合計（更新前・更新後）
           opp: { before:[…], after:[…] }, applied: [{who, action, size, mult:[b1..b5]}] },
  step2: { high, conn, suit, pair, dyn, dynScore, newCard },   // newCard：ターン・リバーのカード分類
  step3: { raMine, raOpp, ra, raEff, na, mid, nutsMine, nutsOpp, checkFlag,
           nutsTop: { mine:[{cls, share, oppPre, oppNow}], opp:[…] } },   // 8.3：最強クラスの手の内訳
  step4: { freq, sizeRaw, sizes:[s1, s2?], slowB1, adjust:[…] },
  step5: { E, bucket, D, V, nutty, blockCall, blockFold, rank, equityMode },
  step6: { cands: [{ act, size, FE, Ec, EV, reason }], delta, tau, probs, rnd, chosen, freqRange, deltaShift },
  step7: { plan, Er, need }                              // ベットしたとき
       | { need, RE, margin, mdf, defense, mdfGuard },   // ベットやレイズを受けたとき
  other: { equityMode, ms, fallback: null | 'legacy:limp' | 'legacy:cold3' | 'timeout' | 'error', note },
  result?: { oppActions:[…], showdown:{ seat, hole } },   // ハンド終了後に足す（11章）
  check?:  { oppWeight, estFE, actual }                   // 同上
}
```

- **書き込み：** 各モジュールは `tr.step3 = {…}` のように自分のステップだけ書きます。書いた値は、そのあと変えません。
- **置き場所：** そのハンドのトレースは `SpecBot.traces` に持ちます。ハンド開始時に空にし、ハンド終了時に `result` と `check` を足してから、直近50ハンド分をブラウザ内に保存します（8.3）。
- **大きさ：** 1件あたり約1.5KB の見込みです。レンジそのもの（1,326コンボの重み）は入れず、バケット別の合計だけを入れます。
- **旧ボットに任せた場合：** `other.fallback` に理由を入れた短いトレースだけを残します。リンプポット、コールドコーラーのいる3BP、時間超過、例外です。発生回数の集計（8章の決定5）もここから数えます。

**説明文（`explain.js`）**

- 入力はトレース1件、出力は12章の出力例の形の文章（結論＋①〜⑦）です。
- テンプレートは、ステップごとに「事実」と「判断」の2つを持ちます。判断の言葉は、12章の対応表を `params.js` の `explainWords` に置き、そこから選びます。境目の数値も同じ場所に置き、指示書の閾値（±5pt など）と共通にします。
- **分岐の網羅：** テンプレートは `(ステップ, 分岐キー)` の表にします。表に無い分岐に入ったら、その段に「説明テンプレート未定義（ステップ名・分岐キー）」と出し、`other.note` に記録します。
  - 例：被ベット時の⑥、マルチウェイ、旧ボットに任せた場合。
- **文章の材料はトレースの数値だけ：** 指示書の出力例③の「BBはこれらの手をプリフロップで3ベットに回すため」のような理由は、トレースの数値から出せません。代わりに `step3.nutsTop` の内訳で書きます（8.3）。

**表示（`index.html` 側）**

- ハンドが終わったら、卓の下に「ボットの判断を見る」ボタンを出します。押すと、そのハンドのボットの全アクションを一覧し、1件ずつ説明を開けます。
- ハンド中は出しません。ボタンを押せるのは `S.done` のあとだけです。
- 画面の見た目は、CLAUDE.md の決まりどおり `design` 担当に渡します。こちらで作るのは、トレースから説明文を返す関数と、ボタンを置く場所までです。
- 実装の順番は、指示書12章のとおり、①記録、②説明文、③表示 にします。

## 5. 判断の流れ（実装）

指示書1章の順番どおりに進めます。順番は入れ替えません。

```
decide(seat):
  snap = snapshot(S, seat)                         // Step0：状態の確定
  if 新しいストリート: streetSetup()                 // Step1：前のストリートの行動で両者のレンジを更新
                                                    // Step2：テクスチャ（フロップは表、ターン・リバーはカード分類）
                                                    // Step3：RA、NA（フロップは表、ターン・リバーはランアウト表から計算）
  if 3人以上: multiway の補正を有効にする
  if toCall > 0: return defense.facing(snap)        // Step7-B（直前の行動でレンジを更新してから判断）
  node = nodeType(snap)                             // Step0 のノード種別（CB/ドンク/プローブ/ディレイド）
  plan = nodePlan(snap, RA, NA)                     // Step4：F、サイズ候補、B1 を残す率
  evals = 自分のレンジ全コンボを評価（Step5）、EV と行動確率を計算（Step6）
  頻度とブラフ比率を調整（Step6-5）
  自分の手の行動を乱数で決める。ベットなら反撃時プラン（Step7-A）を付ける
  trace.finish(tr)                                  // 12章：この判断のトレースを確定（各ステップは計算の途中で tr.stepN に書いている）
  return {act, to}
```

- **ドンク：** 原則チェックです。Step3 で自分側の RA または NA が閾値を超えたときだけ、通常のベット判断に回します。
- **「相手から見た自分のレンジ」の更新：** 指示書3章の表の倍率を使います（Step6 で出した自分の行動確率は使いません）。指示書の「両方を同じ手順で」に従うためです。Step6 の確率はログに残し、校正のときに表の倍率と比べます。

## 7. テスト方針

- **単体テスト（Node、`tests/spec-*.mjs`）：** `bot/spec/*.js` を Node で直接読み込んで、段階ごとの完了条件を確かめます。
  - 例：コンボ番号、フロップの正規化、厳密エクイティ、変換層の合計、バケットの境界、行動確率の式（Δ と τ）、ジオメトリックサイズ（指示書の例：ポット10bb、有効スタック95bb、3ストリートで約86%）。
- **検算（Python、eval7）：** `tools/equity_crosscheck.py` で、無作為に選んだ1,000局面について、JS の結果と eval7 の結果を比べます。
- **局面テスト：** 指示書の例そのものを、固定のカードと履歴で再現して、出た行動を確かめます（8章と9章の例、5章の K72r の検算）。
- **ゲームを壊さない確認：** 既存のテスト（`tests/*.mjs`）をすべて通します。加えて、`ver='spec'` のボットを入れて、Playwright でリングを数千ハンド回し、エラーと止まりが無いことを確かめます。
- **強さの確認：** `tests/ring-bench.mjs` に `spec` を指定できるようにし、v13 と重複配牌で対戦させます（bb/100 と標準誤差）。指示書11章どおり、①の数値を対戦成績だけで調整することはしません。
- **速度：** 1判断の時間を記録し、95パーセンタイル（遅いほうから5%の値）が 0.5 秒以内であることを確かめます。スマホ相当は、Playwright で CPU を 4 倍遅くして測ります。
- **判断トレース：**
  - 毎判断のあと、トレースの必須欄（12章の表の全項目）が埋まっていることを確かめます。
  - 同じ乱数の種で同じハンドを2回回して、トレースが一致することを確かめます（判断とトレースがずれていない証拠）。
  - トレースの `step6.chosen` と、実際にゲームに返した行動が一致することを、全判断で確かめます。
- **説明文：** 分岐キーをすべて並べた表から、テンプレート未定義が1つも出ないことを確かめます。代表的な局面は、出力した文章を固定の期待値と比べます（文の形が崩れたら気づけるように）。
- **CLAUDE.md の約束：** 画面の挙動を変えた部分には、修正前に失敗し、修正後に通るテストを足します。

| # | 項目 | 決定 | 実装での扱い |

| 1 | Step4 の型 | 指示書6章の「型の判定表」に従う | 下の 8.1 |
| 2 | 2つのサイズ | 最大2つ。各サイズの中でバリューとブラフの比率を守る。各ハンドは、Ec が50%を割るサイズを除いた候補のうち、EV が最大のサイズを選ぶ。片方のサイズに入るコンボがベットレンジの10%未満なら、1つのサイズにまとめる | `action.js` で、サイズごとにブラフ上限を計算する。まとめる判定は、全コンボの割り振りが終わったあとに1回だけ行う |
| 3 | 頻度の調整 | 全ハンド共通の補正値 δ（初期値0）をベットの EV に足して、境目を動かす。τ は混ぜる幅として固定する | δ は、目標頻度±10pt に入るまで二分探索で求める（最大20回） |
| 4 | レンジ編集との整合 | ずれた組だけ対局中に計算してキャッシュする。空き時間に表全体を作り直す | 4.2 のとおり。作り直しは、ボットの手番でないときに Web Worker で行う |

追加したパラメータ（δ、相手のレイズ率、f、IP のチェックバックの倍率）は、すべて区分①です。

### 8.1 型の判定表の使い方

指示書6章の補間ルールのとおりです。実効RAとNAを−5〜+5ptに丸め、9つの基準点の間を双線形補間して、目標頻度とサイズを出します。書かれていない細部（静的と動的の間のサイズ、2つ目のサイズ候補の選び方）は、`docs/decisions.md` に記録しました。

### 8.2 コンボ単位の分類（バケット、D、V）

事前計算の表には入れず、ハンド内で計算します（指示書0章の最新版）。ハンド開始時の計算時間の実測と、近似を使う条件は `docs/decisions.md` にあります。

### 8.3 判断トレースで決めたこと（2026-10-25）

1. **保存期間：** 直近50ハンドのトレースを、そのブラウザ内（localStorage）に保存します。履歴画面からも開けるようにします。クラウドには保存しません。キーはユーザーごとに分けます（`UserGate` と同じ考え方）。容量が足りないときは古いものから消します。
2. **数値から出せない理由：** 内訳の数値を記録して、それを書きます。Step3 のトレースに、両者の「最強クラスの手（相手のレンジに80%以上勝つ手）」のうち重みの大きいハンドクラス上位3つと、その各クラスが相手のこのラインのレンジに残っている割合（プリフロップ時点と現在）を足します（`step3.nutsTop`）。説明文の③は、この数値で書きます。

### 自分で決めたこと（確認は不要と判断）

- MTT は対象外です。旧ボットのまま残します（オーナー確認済み）。
  - ただし、完成後にこの新ボットを土台にして MTT 用のボットを作れるようにしておきます。具体的には次の3つです。
    - スタックの深さ、ICM、アンティを判断の外から渡せるように、`Snapshot` に `mode`（'cash' / 'mtt'）とスタック情報を持たせる。
    - MTT のプリフロップレンジ（スタックの深さ別の表）を読めるように、`preflop.js` の読み込み先を差し替え可能にする。
    - EV の計算で「チップの価値」を変換する口（キャッシュでは何もしない）を `hooks` に置く。
- ボットの性格（`loose`、`aggr`、`three`）は、新ボットのポストフロップでは使いません。5体のボットは、ポストフロップでは同じ戦略で打ちます。プリフロップは今のまま（チャート×性格）なので、ボットの個性はプリフロップにだけ残ります。
- 重みの下限 0.02 は、コンボ単位で「元の重み×0.02」を下回らないようにします（カードリムーバルで 0 になったものは 0 のまま）。
- リングでは、前のハンドからスタックを持ち越すので、100bb でないこともあります。これは SPR で扱い、別の扱いはしません。
- 3人以上のポットの相手の反応は、相手ごとに推定します。全員が降りる確率は掛け算で出します。
- 旧ボットのレンジ更新（`narrowRange`）は、そのまま動かします。これは旧ボットと MTT のボットが使う「相手の手の推定」で、プリフロップのレンジ表の編集とは関係ありません。新ボットは自分専用の推定を別に持ちます。レンジ表の編集は、8章の決定4のとおり新ボットに反映します。
