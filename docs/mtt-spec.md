# MTTモード 仕様書（ドラフト v0.2）

状態：**開発前の仕様案**。数値の多くは「初期値（要チューニング）」で、決めるべき点は §10 にまとめた。
前提：リングゲーム（`index.html` の `tab-ring`）の資産を最大限使う。

---

## 0. このドキュメントの結論

1. 添付画像を読み込んで反映済み（v0.2）。ストラクチャーは確定（29レベル、BBアンティ）。**賞金表は添付の数字が合計と矛盾しており、確定できていない**（§3.4）。これだけが残る未確定事項。4枚目の「ボード」は順位表ではなく、**トーナメントクロック画面**だった（§7.3）。
2. 最大の技術リスクは、リングゲームのエンジンが**6人席に固定**されていること（§9）。MTTは8人卓で、ヘッズアップや4人卓も出るため、エンジンの一般化が先に要る。
3. 他の12卓は1ハンドずつカードを配って再現しない。**チップ保存則を守る軽量シミュレーション**で動かし、自分の卓だけを本物のエンジンで動かす（§6）。これで「平均スタック」「残り人数」「ICM」が一貫して計算できる。
4. 1回のMTTの結果は分散が非常に大きい（§8.4）。トーナメント単位の収支で実力を測ろうとすると数百回が必要になるため、**ハンド単位・判断単位の分析**を主役にする設計を勧める。

## 2. 全体像

```
[エントリー] 参加費を引く → 100人を13卓に配席 → 自分の卓でハンド開始
      │
      ▼
[1ハンド進行]  自分の卓＝本物のエンジン（カードを配り、全員が判断）
      │          └→ 経過した「仮想時間」を計算
      ▼
[他卓を同じ時間ぶん進める]  軽量シミュレーション（チップ移動・全員のバスト）
      ▼
[バスト処理 → 卓崩し・人数調整 → ブラインドレベル更新]
      ▼
[自分のバスト or 優勝] → 順位・賞金を確定 → 結果とバンクロールに記録
```

状態は次の4つで持つ。

- **Tournament**：構成（ストラクチャー、賞金表）、仮想時計、現在レベル、残り人数、プール総額
- **Player**（100人分）：名前、スタック、席（卓番号・席番号）、スタイル、バスト順位
- **Table**（最大13卓）：席の配列、ボタン位置。自分の卓だけ手札・盤面・アクションを持つ
- **Hero**：スタック、順位、そのトーナメントのハンド記録

## 3. ゲーム設定の仕様

### 3.1 基本設定

- 参加者：自分＋ボット99人。総チップ＝100人×100,000＝**10,000,000**（以後、チップ総量は不変）
- 初期配席：13卓（8人卓×9＋7人卓×4）。席はランダム
- スタート時点の深さ：100,000÷400＝**250bb**（リングの100bbの2.5倍。序盤はかなりディープ）
- リバイなし。レイトレジなし。アドオンなし
- 参加費の合計＝50,000円×100人＝5,000,000円。**還元率90%＝賞金総額4,500,000円**（残り10%はレーキ扱いで、誰にも配らない）
- 重要な帰結：**実力がボットと同じ人の期待ROIは−10%**。プラスにするには、ボットより10%分強い必要がある（§8.3の指標の読み方に影響）

### 3.2 アンティ

添付のストラクチャーは、アンティの金額がBBと常に同じ。**BBアンティ**（BBが「BB＋アンティ」を一括で払う）として扱う。

BBアンティの扱い：BBがBB＋アンティ（例：L1は400＋400）を出す。プリフロップのコール額はBB（400）で、アンティは死に金としてポットに入る。

### 3.4 賞金表（**未確定**）

添付の「100人規模の賞金シミュレーション例」は、数字が内部で矛盾している。

- 示された1〜6位の合計：675,000＋450,000＋300,000＋（4〜6位が各15〜20万円×3）＝約195万円
- 賞金総額450万円との差額＝約255万円を、7〜15位の9人で分けると**1人約28万円**になる
- ところが同じ表は、7〜15位を「約10万円以下」と書いている

つまり「1位15%・2位10%・3位6.7%」「7〜15位は10万円以下」「総額450万円」は、同時には成り立たない。賞金表は**データとして持ち、コードを変えずに差し替えられる形**にする。確定までの仮置き：

| 順位 | 賞金 | 順位 | 賞金 |
|---|---|---|---|
| 1 | 675,000 | 9 | 240,000 |
| 2 | 485,000 | 10 | 225,000 |
| 3 | 400,000 | 11 | 215,000 |
| 4 | 350,000 | 12 | 205,000 |
| 5 | 315,000 | 13 | 200,000 |
| 6 | 290,000 | 14 | 195,000 |
| 7 | 270,000 | 15 | 185,000 |
| 8 | 250,000 | 合計 | 4,500,000 |

作り方：1位を15%に固定し、全体が450万円になるよう、1/順位^0.475 の比で15位まで配分して5,000円単位に丸めた。かなり**フラットな配分**で、最下位入賞でも参加費の3.7倍になる。現実のMTTは上位が厚いのが普通なので、実際の賞金表を知りたい（§10-Q3）。

## 4. 仮想時計（ブラインドの上げ方）

### 4.1 方針

実時間は使わない。**自分の卓の1ハンドごとに、仮想の経過秒数を足していく**。他卓・ブラインド・残り時間表示はすべてこの仮想時計に従う。

理由：このゲームは相手の動きをスキップして進めるので、実時間と実際のハンド数が噛み合わない。ブラインドの上昇を実時間に結びつけると、速く打つほどブラインドの進行が遅くなり、実戦と違う練習になる。

### 4.2 1ハンドの仮想秒数（初期値）

実戦（オンライン8max）は1時間あたり約65〜75ハンド＝1ハンド約50秒。ライブは約25〜30ハンド/時。まずオンライン相当に合わせる。

```
基本： プリフロップで終了        35秒
       フロップまで見た          +20秒
       ターンまで見た            +15秒
       リバーまで見た            +15秒
       ショーダウン              +10秒
       オールインが入った        +10秒（映像演出相当）
       ランダム変動              ×(0.75〜1.30)の一様乱数
```

平均はおよそ45〜55秒（約70ハンド/時）。**30分のレベルで約36ハンド**、20分で約24ハンド。

**進行速度の設定**：この秒数に倍率をかけられる（×1／×2／×3）。倍率が大きいほど、少ないハンド数でブラインドが上がる。下の §4.4 の通り、×1では長すぎるため、**初期値は×2**（約100秒/ハンド＝ライブ並みの約36ハンド/時）を推奨。

- 自分がフォールドして高速で流れるハンドも、同じ式で仮想秒数を足す（流れが速いだけで、時間は経過する）
- 自分の思考時間は加算しない
- 変動の乱数は、毎ハンドのシードで固定してログに残す（再現性のため）

### 4.3 レベルの切り替え

- 仮想時計が次のレベルの開始時刻を超えたら、**次のハンドから**新しいブラインドを適用する（実戦と同じ）
- 画面の「次のブラインドまで mm:ss」は、レベル残り時間（仮想）を表示
- 休憩（Lv4後10分、Lv8後10分、Lv15後5分）：仮想時計に休憩分を足すだけでスキップする。休憩中は他卓もバストしない。画面には「休憩中」と次の再開時刻を出し、「再開」ボタンで次のレベルへ進む
- Lv29以降：Lv29を繰り返す

### 4.4 想定されるプレイ量（要チューニング）

構造の特徴：持ち点100,000は、Lv1で250bb、Lv4（BB1,000）で100bb、Lv9（BB3,000）で約33bb、Lv15（BB12,000）で約8bbに相当する。**平均スタックはLv9あたりから30bb以下に入り、ほぼ全員がプッシュ／フォールドの領域でバブルを迎える**（ボットのロジックで最重要になる部分）。

優勝までの仮想時間：入賞（15位）に達するのはLv19〜21付近（仮想で約500〜560分）と見込む。**これは推定で、§5.4のシミュレーションで検証する**。

| 進行速度 | 秒/ハンド | 入賞までの自分の卓のハンド数 | 実時間（1ハンド15〜25秒として） |
|---|---|---|---|
| ×1 | 約50 | 約650 | 約3〜4.5時間 |
| ×2（推奨） | 約100 | 約330 | 約1.5〜2.5時間 |
| ×3 | 約150 | 約220 | 約1〜1.5時間 |

長いため、中断と再開（§10-Q7）は必須機能。

## 5. 参加者の減少（他卓シミュレーション）

### 5.1 方針

**チップ保存則を守る軽量シミュレーション**で、自分以外の卓も同じ時間だけ進める。カードは配らない。スタックの大小が結果に反映されるようにする。

判断：「ランダムに毎分何人脱落」のような**単純な脱落率だけ**のモデルは使わない。理由：平均スタック、スタック分布（ビッグスタックの存在）、ICMが、残り人数と矛盾なく計算できなくなるため。

### 5.2 1ハンドの軽量処理（卓ごと）

1. アンティ・ブラインドを集める
2. ハンドの型をスタック深さに応じた確率で選ぶ：
   - **ブラインドスチール／ウォーク**（約50〜55%）：ボタン側の誰かがブラインド＋アンティを取る
   - **小〜中ポット**（約30%）：2人がポット（5〜15bb）をやりとりし、勝者はランダム（スタック大きめがやや有利）
   - **オールイン対決**（スタックが浅いほど確率が高い）
3. オールインの発生確率（初期値）：

| 有効スタック | 1ハンドあたりの確率（卓内の誰かの対決） |
|---|---|
| 100bb以上 | 約2% |
| 30bb | 約8% |
| 15bb | 約20% |
| 8bb以下 | 約45〜70% |

4. 対決の勝者は、実際のプリフロップ・エクイティ分布（コインフリップ約40％、支配されている約25%、その他）を使って確率で決める
5. スタックが0になった人はバスト。**同一ハンドで複数バストした場合は、そのハンド開始時のスタックが多い方が上位**（標準ルール）

### 5.3 同期のとり方

- 全卓が「自分の卓と同じハンド数」を進める（ハンドごとの仮想秒数を卓ごとにばらつかせて、遅い卓は1ハンド少ないことがあってよい）
- バブル（残りが入賞人数＋数人）に近づいたら**ハンドフォーハンド**に切り替える：全卓が1ハンドずつ同時に進め、同ハンドの複数バストは順位決定ルールで処理（実戦のバブルと同じ動き）

### 5.4 検証（必須）

実装時に、**ボットだけで1,000回トーナメントを回すテスト**を行い、次を満たすか確認する。

- どの席の期待収支（ROI）も約0%（実力差なしなら）
- ITM到達時の仮想経過時間、残り人数の推移、ビッグスタックの比率（ITM時に平均の3〜5倍程度）が実戦のオーダーに近い
- チップの総量が常に10,000,000

## 6. テーブル配置・人の移動

### 6.1 卓の数の目標

目標卓数 `T = ceil(残り人数 / 8)`。残り人数が減って `T` が現在の卓数より小さくなったら、卓を崩す。

### 6.2 卓崩し

- 崩す卓：卓番号が最大の卓（または最も人数が少ない卓）
- そこの全員を、空席のある他卓に振り分ける。振り分け先は人数が少ない卓を優先
- 自分の卓が崩れた場合は、「テーブルが崩れました。卓Nの席Mに移動します」のメッセージを出し、新しい卓の7人を新たに表示する

### 6.3 人数のバランス

卓崩しがない場合でも、**最大卓と最小卓の人数差が2以上**になったら、最大卓から最小卓へ1人移す。

- 移動する人：次にBB（またはボタン位置の不利な席）に当たる人（標準的な運用）
- 移動後の席：空席のうち最もボタンから遠い席（ブラインドの二重払い・飛ばしが起きにくい）
- 自分が選ばれた場合も同じルールで移動し、メッセージで知らせる

### 6.4 ファイナルテーブル

残り8人以下になったら1卓に統合。以降は卓の移動はなし。残り2人でヘッズアップ（§9で必要）。

## 8. 結果管理・バンクロール

### 8.1 トーナメント結果の記録

1トーナメントごとに1件保存する。

```
{ id, startedAt, endedAt, buyIn:50000, field:100,
  place, prize, net(=prize-buyIn), hands, 
  reachedITM, reachedFinalTable, bustHandNo, bustLevel, bustStackBB,
  bankrollAfter }
```

- 優勝・バスト時に、順位と賞金を表示して保存
- 結果は一覧で見られ、並び替え・削除はできない（記録の信頼性のため。削除は「全リセット」のみ）

### 8.2 バンクロール

- 初期値：**3,000,000円**（設定で変更可、変更履歴を残す）
- 現在値＝初期値＋Σ(賞金−参加費)
- 参加費を払えない（現在値＜50,000円）場合は、エントリーできない。「バンクロールをリセット」で再開（リセット前の履歴は残す）
- エントリー時点で参加費を引く。**途中放棄は、その時点の順位でのバスト扱い**（嫌な結果の破棄で統計が歪むのを防ぐ。§10-Q7）

### 8.3 表示する指標

- 収支の推移グラフ（バンクロール残高、累積の収支）
- ITM率、ファイナルテーブル到達率、ROI、平均順位、平均バスト時の深さ（bb）、最大ドローダウン（累計の最大下落額）
- バイイン換算（収支÷50,000円）
- ROIは**−10%が「ボットと同じ実力」の基準線**として表示（還元率90%のため。§3.1）

### 8.4 分散についての注意（分析設計の根拠）

§3.4の仮置きの賞金表（かなりフラット）で、実力がボットと同じ人の1トーナメントの標準偏差は**約2.4バイイン**。上位が厚い賞金表なら、これより大きくなる（上位厚め・還元率100%の概算では約3.7〜4.5バイイン）。

- 仮置きの賞金表でも、100回打ってROIの標準誤差は約24%
- 本当のROIが+20%のとき、それを1標準誤差で見分けるのに**約140トーナメント**（上位が厚い賞金表なら約330〜500）
- 1トーナメント約2時間なら、検証に**数百時間**

示唆：トーナメントの収支は「結果の記録」としては重要だが、**上達の指標には使いにくい**。分析の主役は、ハンド・判断の単位（§8.5）に置く。

### 8.5 MTT用の分析（リングの分析にMTT固有のものを追加）

- スタック深さ帯別（〜10bb／10〜20／20〜40／40〜100／100bb〜）の成績と、VPIP・PFR・3ベット
- ステージ別（序盤／中盤／バブル／インマネ後／ファイナルテーブル）の成績
- プッシュ／フォールドの判断の正誤（ナッシュ均衡チャートとの比較）
- オールインのチップEV（運の要素を除いた期待値）
- ICM判断：チップEVで正しいがICMでは誤りだった判断の一覧（バブル周辺の判断力を測る）

リングの「分析」「履歴」は、**ゲーム種別（ring/mtt）のタグで完全に分ける**。MTTのハンドがリングの統計に混ざらないようにする（リングの収支はbb単位で、MTTではブラインドが変わるため）。

## 9. コンピュータのロジック（既存コードとの差分）

### 9.1 現状（リングのエンジン）

- 席数が**6に固定**（`%6`、`POS`、`SEAT_XY`、ボット5人、`S.button` が0〜5）
- ブラインドが**固定**（`BB=100`、SBは50、スタート10,000）
- ポストフロップのボットは100bb前後を前提に作られている
- プリフロップのチャートは6max 100bb（プリフロ練習タブ側にMTT 20bb のオープンレンジだけ既にある）
- ヘッズアップ（SBがボタン）、3〜4人卓のポジション名が未対応
- 保存データ（ハンド記録）は、bb単位の収支に固定

### 9.2 必要な変更

**エンジンの一般化（最優先、全体の土台）**

| 変更 | 内容 |
|---|---|
| 席数 | 2〜8席で動くようにする。ポジション名を人数から決める（8人：UTG/UTG1/LJ/HJ/CO/BTN/SB/BB、4人：CO/BTN/SB/BB…） |
| ブラインド | SB・BB・アンティを変数にする。BBアンティの徴収 |
| ヘッズアップ | ボタン＝SB、ポスト・アクション順の処理 |
| ボタンの移動 | 脱落者がいる場合のボタン処理（ダッドボタンではなく、次の生存者に進める簡略ルール） |
| 座席表示 | 8席の座標（PC・スマホ） |
| 金額単位 | チップとbbの両対応（初心者モードは除外） |

**プリフロップのレンジ（スタック深さ対応）**

1. 有効スタック（自分と、自分より後ろの最大スタックの小さい方）を計算
2. 深さ帯のチャートを使う：100bb以上はリングのチャートを8人卓向けに調整（UTG1/LJを追加）、40bb／30bb／20bb／15bb／10bbは深さ別のチャート、7bb以下はプッシュ／フォールド
3. 隣り合う深さのチャートは**補間**する
4. アンティ込みで見積もる（BBアンティありでは、プッシュレンジが広がる）
5. **自分のスタック**と**卓の平均スタック**の比で調整：
   - ビッグスタック（平均の1.5倍以上）：オープン・3ベットを広げる
   - ミドルスタック（バブル周辺）：リスクを避けて絞る（ICM）
   - ショートスタック：プッシュ／フォールドに寄せる
6. 必要なデータ：プリフロ練習タブのMTTボックス（現在は20bbのオープンのみ）を、10〜40bbまで拡張する。**プッシュ／フォールドのチャートはナッシュ均衡の計算で自動生成**する案（手入力より速く、アンティ込みで正確）

**ICM**

- 方式：ICM（マルムース・ハーヴィル方式）で、残り全員のスタックと賞金表から各人の賞金期待値を計算
  - 残り人数が12人以下：全探索（ビットマスクDP）で厳密解
  - それより多い場合：入賞人数だけを見る近似（モンテカルロ）
- ボットの使い方：オールイン／コール判断で、**バブルファクター**（負けた時の賞金期待値の損失÷勝った時の利得）から、必要エクイティを引き上げる
- 計算の頻度は、1ハンドに1回（スタックが変わるたびに全員分は計算しない）
- ボットごとに**ICMの意識の強さ**を変える（完全に守るボットばかりだと、実戦より保守的になるため）。強さは0〜1のパラメータ

**ポストフロップ**

- ロジックは当面そのまま使う。ただし、100bb前提の閾値（例：`to>=maxTo*0.9` のコミット判定、スタック比に依存する判断）を、SPR（スタック÷ポット）別に点検する
- 250bb（深い）や15bb以下（浅い）では、リングと別の挙動が必要になる可能性が高い（浅い場合は「フロップで即オールイン」が主になる）
- 点検の結果、修正が大きい場合は、MTTの初期リリースの範囲外とする（§11）

**ボットのプロフィール**

- リングは5人固定。MTTは**99人**必要なので、名前の生成と、`loose／aggr／three` の分布を用意する
- 自分の卓に出てくる7人だけが「見える」ボット。卓が変わると別のボットに入れ替わる
